## 出题人讲解

> 盲区正常，这块是真的少有人讲。而且你手里已经有那把钥匙了，只是没往这上面用——你上一题自己说的："采样出来的不是 logits 的分布图，而是一个 token。"
> 那就在"选出那一个"之前动手脚。
>
> 格式控制有三档强度，差别是本质的：
>
> **第一档，prompt 里说"请输出 JSON"。** 这是请求。模型大部分时候会照做，因为训练里见过无数 JSON。但它随时可能在前面加一句"好的，这是您要的结果："，或者用中文引号，或者最后少一个括号。你在跟一个概率分布讲道理。
>
> **第二档，给几个例子。** 更强的请求。还是请求。
>
> **第三档，在采样那一步动手。** 这一档和前两档不是程度差别，是物理差别。
>
> 第三档具体在干什么：模型每一步吐出来的，是词表里所有词的分数——十几万个词，每个一个分数。采样器从里面挑一个。约束解码干的事是：在挑之前，先把"此刻不合法"的词的分数全部设成负无穷。
>
> 举个具体的。假设已经输出到这里：
> ```
> {"name": "张
> ```
> 下一个词有哪些是合法的？任何能接在字符串里的内容，或者一个收尾的引号。而 `{`、`[`、一个新的字段名——这些在此刻都是非法的，因为 JSON 语法不允许。于是那些词的分数被抹成负无穷，采样器根本看不到它们。它只能在合法的那些词里挑。
>
> 再往前走一步，输出到 `{"name": "张三", ` 的时候，合法的下一步只剩下"一个新字段的引号开头"——而如果 schema 规定了下一个字段必须叫 `age`，那么合法的词可能只剩一个。这时候采样连选择都没有了，只能吐出唯一那个。
>
> 看清楚这个动作的性质：**它不是让模型更愿意守格式，是把不守格式这个选项从牌桌上拿走了。** 输出不可能是非法 JSON——不是"很少"，是数学上不可能。
>
> 而"此刻什么合法"这个判断，是一段确定性代码在跟着你的 schema 一步步走。它不理解你要什么，它只知道语法允许什么。
>
> 你应该认出这个形状了：这跟我们看 Codex 那张十一个格子的白名单是同一个动作——不是拦坏的，是只放行能证明合法的。**Default FAIL 在采样层的版本。**
>
> 现在说代价，两条，都是生产级的东西。
>
> **代价一：字段顺序，就是推理顺序。** 模型是从左往右生成的，它没法回头改。所以这两个 schema 效果天差地别：
> ```
> {"answer": ..., "reasoning": ...}     ← 灾难
> {"reasoning": ..., "answer": ...}     ← 正确
> ```
> 第一个逼着模型先把答案说出来，再去补理由。它已经把答案钉死了，后面的"推理"只能是给结论找补——这就是我们说过的"先答后编"，你亲手用 schema 制造了它。第二个让它先展开，答案在推理的末尾自然落下。**一个字段的顺序，就是要不要 CoT 的决定。** 这条大部分人写 schema 的时候完全没意识到。
>
> **代价二**——这条你会喜欢，因为它直接接上一题。如果你的 schema 写着"`birthday` 是必填字段"，那么当模型不知道张三的生日时，它必须填一个东西进去。合法的输出必须有这个字段，采样器不允许它跳过。**你用 schema 强迫它编了一个日期。**
>
> 这是在结构层面重演 SFT 那道工序——你又一次把"我不知道"这个出口堵死了，而且这次是物理堵死，比训练偏好还硬。
>
> 所以 schema 设计有一条必须遵守的纪律：**永远留不确定性的出口。** 字段允许为空、枚举里加一个 `unknown`、配一个 confidence 字段。**一个没有"我不知道"选项的 schema，是在用工程手段制造幻觉。**
>
> 最后，我第三个提示的答案：
> 工具返回的结构化信封，是把**确定性世界的信息翻译进概率世界**——让模型能"看见"成败。
> Structured Output，是把**概率世界的输出翻译回确定性世界**——让代码能解析它。
> **两个方向，同一道接口。** 这就是你《两种坐标系》里那个"翻译协议"的完整形态。你当时写到接口那里停住了——这就是那个接口的两个方向，各自的工程实现。

### 杀手句

> Structured Output 的本质不是"让模型输出 JSON"，是把格式约束从"请求"降级成"物理限制"——在采样前把非法选项抹掉，让违规不可能发生。而它的代价必须被设计：字段顺序决定推理顺序，必填字段会强迫幻觉。

## 第一轮追问（confidence 这个数怎么衡量）

> 你这个反问很关键，而且它戳破了我上一条里一个含糊的地方——"confidence 字段"这四个字，藏了两种完全不同的东西，我该分开说的。
>
> **第一种：模型自己写的那个数。** `{"answer": "1985-03-12", "confidence": 0.9}`——这个 `0.9` 是怎么来的？它是被采样出来的一个 token。和 `1985` 一样，和句号一样，走的是同一套流程。
> 关键在这：**模型看不见自己的 logits。** 它生成"0.9"这三个字符的时候，没有任何通道让它去读"我刚才那个日期的概率分布有多平"。它是在模仿——在训练语料里，这种语境下的置信度字段通常写多少，它就写多少。
> 所以那不是内省，是又一次续写。而且它继承了全部原罪：RLHF 教过它自信，所以它报的数普遍偏高，什么都写 0.85、0.9。
>
> **第二种：logprobs。** 这个是真的。模型每一步的概率分布确实存在，API 也确实能吐出来（`logprobs` 参数）。你拿到的是模型的真实内部状态，不是它的自我描述。
> 但这里有个陷阱：**token 的概率，测的是"下一个字该怎么写"，不是"这件事是不是真的"。**
> - 答案对，但 logprob 很低：问一个日期，模型可以写"3月12日"、"March 12"、"1985-03-12"——三种写法瓜分了概率。第一个 token 的分布看起来很平，但它对这个事实其实很确定。你测到的是**措辞的犹豫**，不是事实的犹豫。
> - 答案错，但 logprob 很高：一个编出来的 API 名字，一旦开了头，后面每个 token 都顺理成章、概率极高。**幻觉可以是高置信的。**
>
> 那什么真的管用？按可靠度排，三档：
> - **最弱：模型自报的数。** 别把它当概率读。
> - **中间：跑多次看散没散。** 同一个问题，温度调高，跑五次。五次都答 1985-03-12 → 稳。五次给出五个日期 → 那个平坦分布自己现形了。这一招好在哪：它绕开了措辞问题。你比的是五个答案的**意思**一不一样，不是 token 一不一样。（学术上叫**语义熵**——把采样结果按意思聚类，再算熵。）代价是五倍成本。
> - **最强：外部验证。** 这个引用真的存在吗？这个 API 真的能调通吗？——不问模型任何事，直接去查。不试图读懂它的自信，而是绕过它的自信。
>
> 现在我要修正我上一条的重点，因为你问得对。我把三个方案并列了，但它们强度差很多，该排序：
> **强的是 nullable 和 `unknown` 枚举。** `"birthday": null`，或者枚举里加一个 `unknown`——这是一个二值的、诚实的出口。模型选了它，就是明确表态"我不填"。没有精度问题，因为它根本不是个数。
> **弱的是 confidence 数字。** 而且如果非要用，别用 0 到 1 的浮点数——那是假精度，模型写"0.73"纯属瞎凑。用粗档位：`certain | likely | uncertain`。粗颗粒反而更抗噪。
> 但结构上那条判断不变：**字段的价值不在那个数准不准，在于它给了模型一条"不承诺"的合法路径。** 没有这个出口，schema 强迫它必须填一个日期。有了出口，至少"它选择走了出口"这件事本身，是真信息。
> 所以准确的说法是：schema 要留出口，出口首选 nullable 和 unknown，confidence 只是聊胜于无的补充。我上一条把三个并列了，是我说糙了。

## 出题人回应

> 两处我都欠你，一个个还。先还 confidence，因为我确实答偏了。
>
> 你问的是"**这个数怎么衡量**"。我给你最直接的答案，而且这个答案不太舒服：
> **如果这个数是模型自己写进 JSON 的，那它什么都没衡量。**
> 模型生成"0.9"这三个字符的时候，走的是和生成日期完全一样的流程——采样。**它没有任何通道能读到自己刚才那个日期的分布有多平。** 它是在模仿"这种场合下人们通常写多少"。
> 所以"让模型输出 confidence 字段"这件事，本质是**表演**。你拿到一个看起来像概率的数字，但它背后没有任何测量。
> **真正的数只有一个来源：你的代码去算，然后附上去。** API 返回里有 logprobs，那是模型的真实内部状态。你可以拿关键字段那几个 token 的概率算一个数，由你的程序写进这条记录里——那是真的。
> 区别就是这一句：**模型写的 confidence 是它编的；你算出来附上的 confidence 是测的。** 同一个字段名，两种完全不同的东西。
> 所以我上一条那个建议该改成：**别让模型写 confidence。** 要出口，就给 nullable 或 `unknown`。要数字，你自己在外面算。
>
> 现在还约束解码这笔，这个值得讲透，因为它确实反直觉。
>
> 先回答"五万个都过一遍？"——**是的，真的是五万个都过一遍。而且这不贵。**
> 关键在于对比：产生这五万个数字，模型刚刚做了**几十亿次乘加运算**（走完全部层）。而屏蔽它们，是对一个五万长的数组扫一遍，把不合法位置的值改成负无穷——**五万次加法**。几十亿 vs 五万。后者在总耗时里基本看不见。
> 打个比方：烤一个蛋糕要一小时，切之前挑掉几块不能吃的，要三秒。你不会因为"还要挑"就觉得这事儿不划算。
>
> **第二个问题才是真正的技术点：怎么知道五万个里哪些合法？**
> 如果每一步都拿语法规则去挨个检验五万个 token——那才是灾难。所以真实实现不这么干。
> **真实做法是：生成开始之前，先把 schema 编译成一台状态机。**
> 你可以这么想：schema 描述的合法 JSON，其实是一张有限的"路线图"。每个时刻你站在图上某个位置，从这个位置能往哪走，是提前算得出来的。所以在开跑之前，程序把这张图走一遍，建好一张表：位置 A → 允许这批 token；位置 B → 允许那批。
> 跑的时候，你只需要知道"我现在在哪个位置"，**查表**，拿到允许集合，其余全屏蔽。没有五万次判断，只有一次查表。
> **昂贵的活在开跑前干完了一次。** 这就是 Outlines 那类库在做的事。
>
> **第三个问题，你问得最好："下一个字段一定是固定好的吗？"**
> 不一定，**而且我上一条说得太绝对了。** 准确的画面是这样的——
> 在**结构的接缝处**，约束极紧：
> - 刚吐出 `{` → 下一个只能是 `"`。其余四万九千九百多个 token 全被屏蔽。
> - 刚吐出 `"name": "张三"` → 只能是 `"` 收尾，或者继续写字符串内容。
> - 一个 enum 字段，只允许三个值 → 引号一开，只有能拼出这三个词的 token 是活的。
>
> 在**自由内容**里，约束几乎为零：
> - 正在写 `"summary": "` 后面的正文 → 除了引号和转义，几乎所有 token 都合法，模型完全自由。
>
> 至于字段顺序——取决于 schema 写得多严和实现怎么做。有的实现强制按 schema 里的顺序走（那就真被钉死了），有的允许必填字段任意顺序（那么下一步"可以是剩下三个字段中任何一个的开头"，仍然是个受限但有选择的集合）。
> 所以准确的说法是：**结构被强制，内容仍自由。** 屏蔽掉的只是语法上不可能的东西，不是"模型想说的话"。你的直觉里那个"感觉有很大模糊"——模糊确实在，但它全部落在自由内容区，而那正是它该在的地方。
>
> 最后给你一个真实的代价，它恰好是你那句"听上去很诡异"的直觉在指向的东西：
> **token 的切分边界，和语法的边界对不齐。** 模型词表里可能有一个 token 就是 `age":` 这样跨越了语法边界的组合。
> 于是会出现这种情况：模型本来想一口气吐 `age":`（一个 token，它最顺的写法），但状态机此刻只允许 `"`，于是它被迫走一条它训练时很少走的拼法。
> 结果是：**输出仍然合法，但模型被推离了它熟悉的分布，质量可能下降。**
> 这就是约束解码真实的代价——**不是慢，是你可能把模型逼进它不擅长的表达路径。** 这也是为什么严格 schema 有时反而让答案变差，而不只是变整齐。

## Q06 出题（待答）

> 第六题：Function Calling 与 RAG 的区别和联系，什么时候用哪个。
>
> 这题你能答，但我要提前堵一个坑：题库的标准答案（实时/结构化 → FC，离线/非结构化 → RAG）是二〇二三年的分法，2026 年已经不太站得住了。
>
> 所以你答的时候，除了给出那个常规分法，再想一想：**Function Calling 里如果那个"函数"就是"去搜文档"呢？那它到底算 FC 还是算 RAG？**
>
> 从这个问题切进去，你会摸到 2026 年真正的分界线在哪。
