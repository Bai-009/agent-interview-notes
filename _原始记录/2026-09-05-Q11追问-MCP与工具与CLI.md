## 只需要分清三个问题

| 问题 | 答案叫什么 |
| --- | --- |
| **能做什么事？** | 工具 |
| **模型怎么开口要求做这件事？** | function calling |
| **运行模型的那个软件，怎么从外面接进一件别人做的工具？** | MCP |

工具是**一件事**，function calling 是**模型开口的方式**，MCP 是**软件对外接东西的方式**。三个词回答的是三个不同的问题，所以谁都不等于谁。

## 用你自己说过的话放一遍

你 Q08 说过：**模型只有请求权，没有执行权。**

- 模型开口说「帮我查一下天气」——这个开口的**固定格式**，就是 function calling。
- 听到这句话去执行的，是运行模型的那个软件（Claude Code、Cursor）。它要么自己会做，要么去找外面的程序做。
- 「去找外面的程序」这件事怎么统一起来，就是 MCP。你首答说的 USB 就在这个位置：USB 是插口标准，U 盘是插上去的东西。

**关键一句：模型从头到尾只做了「开口」这一件事。它不知道、也不需要知道那件事最后是软件自己做的，还是通过 MCP 转给外面的程序做的。在模型看来，两种工具长得一模一样。**

## 两个混淆分别错在哪

**「MCP 是插件」**——把**插口标准**说成了**插上去的那个东西**。你装的那个东西是一个按 MCP 标准写出来的程序（记录里叫 MCP 服务器），它才是「插件」。MCP 本身是标准，装不了。这就是你首答里 USB 和 U 盘那一步，你当时已经自己标出来了。

**「工具是 function calling」**——把**要做的事**说成了**开口的方式**。开口的方式只有一种，事有一万件。而且同一种开口方式，那件事可以是软件自带的（Claude Code 自己会读文件），也可以是 MCP 从外面接进来的（查 GitHub）——模型自己分不出来，说明它俩不是一回事。

## 记这一句就够

> **工具是事，function calling 是模型开口的方式，MCP 是软件接外面工具的方式。模型只负责开口；接不接外面的程序，是软件的事。**

## CLI 和 MCP 的区别

终点一样——都是去操作 GitHub。两条路：

**CLI 这条路**：Claude Code 自带一只手——**终端**。模型在终端里敲 `gh pr create`，跟你自己在终端敲一样。「gh 怎么用」这件事**在模型脑子里**（训练时学过），登录状态**在你电脑上**（你之前登录过一次）。Claude Code 官方文档就推荐这条：「CLI 工具是和外部服务打交道**最省上下文**的方式」；我此刻的终端工具说明里也直接写着「GitHub 操作用 gh」。

**MCP 这条路**：GitHub 的 MCP 把几十件事列成几十个工具，**每个带一份说明书塞进上下文**；模型照说明书填表；背后那个服务**拿着登录状态**去调 GitHub。官方给 MCP 的一句话定位：「为某个外部系统提供专门的工具，**连接和登录由那个服务负责**」。

**区别一句话：CLI 这条路要求「有终端」，MCP 这条路不要求。**

| | CLI 路 | MCP 路 |
| --- | --- | --- |
| 说明书在哪 | 模型脑子里，不占上下文 | 上下文里——GitHub 的 MCP 35 个工具约 26K token，你记录里那笔账 |
| 登录在哪 | 你的电脑，终端里的程序都能用 | 那个服务手里，它替你拿着 |
| 谁用得了 | 只有**有终端**的：Claude Code | 任何软件，包括**没有终端**的：网页版聊天 |

所以 Anthropic 两条都做，不矛盾：Claude Code 有终端，凡是有命令行工具的服务（gh、aws、gcloud）不装 MCP 也够得着，还更省；网页版没有你的终端，要碰 GitHub 只能靠 MCP（那边叫 connector）。

模型不认识的命令行工具怎么办？官方给的办法是让它先跑一遍 `--help` 自己学，或者你写个 Skill（菜谱）。这正好接回 Q11 那两个词：**CLI 路把「够得着」交给终端、把「会不会用」交给模型或菜谱；MCP 路把两件事打包——说明书随工具一起来。**

## 记这句

> 工具分两个来源：软件自带的、MCP 接的。操作 GitHub 走 CLI，是用自带的终端这只手；走 MCP，是接一个替你拿着登录、随身带说明书的服务。有终端时前者更省，没终端时只有后者。

依据：Claude Code 官方的 [Best practices](https://code.claude.com/docs/en/best-practices)（「Use CLI tools」一节）和 [Extend Claude Code](https://code.claude.com/docs/en/features-overview)（「MCP vs Skill」一节）。哪句不清楚，指给我。

**第四轮 · 维护方：**

**总结对了，四条里四条都对。** 两处补精度，不算纠错：

**① 「agent 去调用……发送到服务端」**——「agent」里装着两样东西：**模型**和**运行它的软件**（Claude Code）。开口的是模型，发出去的是软件；结果回来也是软件先收到，再摆进模型的上下文。模型两头都不碰服务端。要拆开说，是因为「要不要放行」那一步就卡在软件这一层——Q08 的请求权 / 执行权，Q20 会再用到。

**② 「CLI 不需要额外配置说明」**——准确说是**不需要每件事一份说明**。终端本身也是一个工具，也有一份说明书，但只有一份，几十件事共用；MCP 是每件事一份。差的是数量，不是有没有。再补一条已经教过的：Claude Code 现在默认只先给工具的**名字**，用到哪个再给哪个的说明书——记录里「渐进式披露住在客户端」说的就是这个，所以 26K 那笔账是全量加载时的数，今天默认没那么贵。

其他三点原样成立：

- 命令是**接龙**出来的——这个词用得准，和 Q04「采样出来的是一个 token」是一回事。
- MCP 服务器可以是本机另一个进程，也可以在远端——规范原文「Can be local processes or remote services」。
- 工具的使用说明必须给到——对，而且**这就是两条路的全部差别**：说明书在上下文里，还是在模型脑子里。

一句话收：

> **CLI 路：一只手（终端）+ 模型脑子里的说明书。MCP 路：一份契约 + 背后一个服务 + 随工具来的说明书。模型在两条路上都只做「开口」这一件事。**
