> 📌 查证（2026-11-03，读的是来源的摘要或关键段落，不是全文通读）：
> - **sink 看位置不看内容**：[arXiv:2309.17453](https://arxiv.org/abs/2309.17453) §3.1，开头四个 token 换成换行符，sink 照样出现；§3.3 的预训练 sink token 实验只用了 160M 小模型，证据小。
> - **sink 的机制**：[arXiv:2410.10781](https://arxiv.org/abs/2410.10781) §1 / §3.1，首 token 的 key 与其他 token 的 query 夹角普遍小；hidden 范数大，但 key、value 范数小。§7.3 把 sink 的 value 固定为零，损失几乎不变；拿掉学到的 sink 结构则性能明显下降。作者用「可能」的口气。
> - **CoT 的形式化结论**：[arXiv:2402.12875](https://arxiv.org/abs/2402.12875)（ICLR 2024）摘要：无 CoT 时，常数深度、常数位精度的 transformer 只能算 AC⁰（AC⁰ ⊊ TC⁰）；有 T 步 CoT，可算任何规模为 T 的布尔电路能算的问题（需要嵌入维度随输入长度的对数增长）。实验任务摘要里有：置换群复合、迭代平方、电路值。「层数越浅受益越大」摘要里没有，未核，**不引用**。
> - **指令漂移**：[arXiv:2402.10962](https://arxiv.org/abs/2402.10962)（COLM 2024）摘要：八轮之内出现明显的指令漂移（上限，不是固定时刻）；作者归因于长对话的注意力衰减（假设）；提出 split-softmax。
> - **指令层级**：[arXiv:2404.13208](https://arxiv.org/abs/2404.13208) 摘要：训练模型选择性忽略低权限指令；对训练时未见过的攻击类型也大幅提高稳健性；能力损失小。
> - **首 token 的功能解释**：[arXiv:2504.02732](https://arxiv.org/abs/2504.02732)（Barbero 等，2025）摘要：论点是 sink 让模型避免过度混合信息。这是功能解释，不是加分。

> 你说由代码写出信号。这个信号里具体要有什么，你才认它算完成？

**用户：**

> 不太清楚

**维护方**：没关系，换个小一点的问法。

> 假设代码真的去跑了测试，最后输出一行「全部通过」。可本来一共有 10 个测试，那次只跑了 8 个。光看这一行「全部通过」，你能发现少了两个吗？

**用户**（2026-11-23）：

> 不能，看不出来少了两个

**维护方**：对，从这一行看不出来。

> 那要发现少了两个，你手里事先得有什么？

**用户：**

> 要有一份清单，写明一共有哪些测试

**维护方**：对。有了清单，就能一项一项对：清单上写着 10 个，结果里只有 8 个，差的那两个就露出来了。

> 这份清单，该由谁来写？

**用户：**

> 代码来写

**维护方**（压缩）：不让模型来写，这一半对；已拆到第三步，给答案。清单要在 Agent 动手之前就定好，而且 Agent 改不了：如果检查那一刻才现扫，而 Agent 删了那两个测试或标成「跳过」，扫出来 8 对 8，照样通过。判断完成靠三样不经过模型的东西：事先的清单、代码自己跑、逐项对（「跳过」也算没过）。点破钥匙：Q08「计划要变成能逐项打勾的清单，才能对账」。

### 用户的追问与质疑

**用户：**

> 我在想是否有更好的解决方案，而且大多数人应该不会在开始前制定好测试方案吧

**维护方**（压缩）：认两处。一处说得容易误会：要的不是有人事先写方案，是「拿来对照的东西不能出自 Agent，也不能让它改」；有两样不用人准备——Agent 动手前的样子（开工时代码自动记下现有测试，存在 Agent 碰不到的地方），团队已有的 CI（前提是 Agent 改不了它的设置）。一处确实漏了：Agent 为新功能自己新写的测试，没有任何事先参照，等于自己出题自己答，只能换检查的人——人看一眼新测试，或另开一个干净的 Agent 审（仍是模型，只能多发现错）。更好的说法：拿来对照的东西，不能出自被检查的那一方。

**用户：**

> 这道题，想告诉我什么？想考察我的是什么？

**维护方**（压缩）：三层——会不会信模型的汇报、判断交不交给代码、代码拿什么去对；前两层第一句答到，卡在第三层。特意写「两个没跑」而不是「没通过」：少做的事不报错，只有拿「本来该有哪些」去对才看得见（Q08 清单对账；Q09「没有事件的失败，在系统里不存在」）。说退款题与本题是同一道题换了场景、「两次卡在同一处」——后半句在本轮末撤回（见下）。

**用户：**

> 我其实还没明白这个流程，因为在我心里觉得，如果我天然就知道结果是什么样，把测试做出来，这件事情就挺诡异的。可能是我不懂开发的原因，但是现在大家都在vibe coding，很多时候的确没有对应的测试的use case

**维护方**（压缩）：认错——题和讲解都默认用户懂测试与开发流程。三句：测试是把已经知道的「什么叫对」写下来，让程序每次自动查，知道结果正是能写测试的前提；没有测试时，判断完成的是人自己，亲手试一遍；眼睛只看得到去看的地方，测试让没人看的地方也有人看着。计算器例子（2 + 3 = 5，测的是计算器不是 5；第 37 轮改乘法碰坏了加法）。用户其实一直在用测试：本仓自检脚本（11-22 拦下禁用词、列出没核实的量词）。vibe coding 没写测试：东西小就自己试；东西多了，用大白话说清「什么叫对」，让 Agent 写成测试并讲给你听，要紧的几条亲手再试。检查问题：

> 自检脚本这个文件，我也改得动。照刚才那条，这算不算问题？

**用户：**

> 能改，这是没问题，但是我看现在比较前沿一点的实践，比如Grok Bot的那个工程师，laurn tan会有新的看法

**维护方**（压缩）：联网查了 Lauren Tan 2026-11 的演讲 All Code Is Slop (Except Mine)。读到第一部分的自动字幕稿（[SozAI](https://sozai.app/transcript/spacex-ai-engineer-lauren-tan-part-1/)）和一篇二手摘要（[AI EngineerGuide，2026-11-15](https://aiengineerguide.com/til/all-code-is-slop-except-mine-by-lauren-tan/)），原视频未看 ⚠️。转述的要点：审查意见尽量写成程序规则（CI 里禁掉某种写法），更好的是让错的写法写不出来；规则文件和自动审查机器人算软的，Agent 会忘，CI 是硬的；让 Agent 把程序真跑起来看；环境事先建好（改造代码库提交了 600 多次改动），没有护栏的 vibe coding 原型会跑偏；放手分三步（本机 → 云端 → 自动合并）；演讲者自己提醒不能照抄，他们的 token 不限量。判断：与「必须成立的交给程序去查」不冲突，是同一条做到了头；「Agent 能不能改检查」，两份材料都没提。对「能改，没问题」拦一下，换小问法：

> 假设我写了一个禁用词，自检报错了。要让它不再报错，最省事的改法是什么？

**用户：**
