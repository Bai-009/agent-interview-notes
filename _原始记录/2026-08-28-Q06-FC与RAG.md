## 反馈

> 这一答你把题目本身推翻了，而且推得对——**这道题问的就是一个类别错误，能看出来才是满分。**
>
> 先确认你的自我修正：**是的，Function Calling 指的就是模型输出的那个东西。**
> 它的全部内容是：模型这一轮不吐散文，而是吐一个结构化的请求——要调哪个工具、参数是什么。仅此而已。至于那个工具背后是搜索引擎、向量库、数据库、还是派一个子代理去干活——**FC 一概不管。**
>
> 所以你那句"与其叫工具调用，不如叫模型动作"，是准的。而且你举的例子恰好是真的：**Claude Code 里派子代理，就是通过一个叫 Task 的工具实现的。** 派子代理在协议层就是一次工具调用。
>
> 而且注意 FC 和上一题的关系：**FC 就是 Structured Output 用在"我要做什么"这件事上**，加一条 dispatch 约定（外面的代码看到这个结构就去执行），再加一段后训练（教它什么时候该吐这个而不是吐散文）。结构化输出是出口，结果信封是入口——一去一回，就是模型和确定性世界的完整接口。
>
> 所以这两个东西根本不在一个层面：
> - **FC 是一种机制**——关于模型输出长什么样。
> - **RAG 是一种架构模式**——关于上下文里的信息从哪来（先检索、后生成）。
>
> **它们不互斥，而且可以互相实现。** 经典 RAG 完全不需要 FC：代码在模型看到问题之前就检索完、塞进 prompt 了，模型全程没有选择权。而 agentic RAG 正是用 FC 实现的——模型自己决定要不要搜、搜什么。
>
> **题库那个答案（实时结构化 → FC，离线非结构化 → RAG），2026 年已经塌了。**
>
> 一个反例就够：**Claude Code 检索代码。**
> 按题库的分法——代码库是离线的、非结构化的、私有的文档，标准的 RAG 领地。
> 但它用的是什么？**grep、glob、read 三个工具，全走 FC。** 而且它是把已经建好的向量检索**拆掉**才换成这个的。
> **最该用 RAG 的场景，行业头部产品用 FC 干了，而且效果更好。** 你要是按题库那张表答，面试官追问一句"那 Claude Code 怎么回事"，就穿了。
>
> **那真正的分界线在哪？在决定权。**
>
> | | 谁决定要不要检索 | 什么时候检索 | 检索错了会怎样 |
> | --- | --- | --- | --- |
> | 经典 RAG | 代码 | 生成前，一次 | 模型不知道自己拿到的是错料，照样自信作答 |
> | FC / agentic 检索 | 模型 | 循环内，按需多轮 | 模型能看到结果不对，改词重搜 |
>
> 这就是同一根轴——我们一路在推的那根：**决定权放在代码里，还是放在模型里。**
>
> 它还决定了成本形状：经典 RAG 是一次固定开销；agentic 是按需多轮，难查询上更贵但更准，简单查询上纯浪费。
>
> 所以生产上怎么选，判据不是"数据是什么类型"，是三条：
> **一、这个检索用不用得着迭代？** 一次 top-k 就够（FAQ、明确的事实查询）→ 预检索省钱省延迟。需要"先找到线索、再顺藤摸瓜"→ 交给模型多轮。
> **二、query 和语料的词对不对得上？** 精确标识符、函数名、错误码 → 字面检索加循环。跨语言、同义改写、概念性 → 向量。
> **三、语料活不活？** 每天在变 → 别建索引，现查。基本静态 → 索引摊得起。
>
> 而且现实里最常见的是混合：底下是向量库，但把它包成一个工具交给模型调——**检索用向量，决定权在模型**。这时候问"这算 FC 还是 RAG"，就已经是个没意义的问题了。

### 杀手句

> FC 和 RAG 不是二选一，它们不在一个层面：FC 是模型输出的形式，RAG 是上下文的来源。真正的选择题只有一个——检索的决定权，交给代码还是交给模型。
