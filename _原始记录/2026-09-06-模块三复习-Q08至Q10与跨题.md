**维护方**：「有机会」留得准，Q10 会用到；后半句猜测是真实做法。再小一步：第 5 轮的结果出现在第 38 轮的输入里——是模型自己一直带着它，还是每一轮都有人重新把它放进去？谁放的？

## Q09

**用户：**

> 因为自己的context不够，比如说调研10个网站，全部都是主agent去调的话，context里面塞满了tool_result，那么请问，context就那么多，我调研了一个问题发现context爆了，或者模型的总结也很烂。这个时候用sub-agent去做，那么我的主agent拿到sub-agent的回复，不就可以更省context空间吗？当然有利有弊，这样主agent看到的是sub-agent的回复，质量取决于sub-agent的极限。

**维护方**：答满，第二问（有损压缩）也顺手答了。追一句：压缩过的东西找不回来。下发任务和收回复的时候，你能做什么，让主 agent 事后还有机会去核？

**用户：**

> 让sub-agent去标注上来源，主agent可以自己去对应的地方核查

**维护方**：对，回报留指针。下发那头呢——该不该让它继承主 agent 的全部上下文？

**用户：**

> 那当然不，sub-agent不是说开一个新窗口，sub-agent对于主agent也是一个工具，是规定好类型的。继承上下文不要钱吗？input也很贵的，我主agent里还有缓存命中。sub-agent的系统提示词也是写好的，然后给sub-agent的当下的提示词是主agent给的。

**维护方**：四点全在；最后一条就是「下发要自包含」。一处措辞：它确实是一个新的干净上下文窗口，只是不是手动开的，是当工具调出来的。第三问：子 agent 崩了、卡住了、跑偏了。主 agent 怎么知道？三种一样吗？

**用户：**

> 前两种是tool_result才能知道，第三种本身sub-agent就把信息传递到主agent的context中了

**维护方**：崩了对。卡住要拦：子 agent 卡住了，那份 tool_result 什么时候到？

**用户：**

> 超时的时候

**维护方**：对——没有超时它永远不到；卡住本身没有事件，超时是造出来的事件。再追：这个闹钟谁来响——让那个卡住的子 agent 自己数时间，行不行？

**用户：**

> 肯定不行啊，肯定是程序在控制

**维护方**：对，程序在外面数（Q09 记录里那个 5 分钟超时堵 7 小时的事故）。跑偏那种：它不崩不卡、正常返回一份结果。从外面看有区别吗？靠什么发现？

**用户：**

**维护方**（拆一步）：跑偏的那份结果里会写着「我跑偏了」吗？——它和好结果一模一样。那你两问之前说的「让子 agent 标注来源、主 agent 去核」，是用来对付这三种里的哪一种的？

**用户：**

**用户：**

> 算吧，并不确定

**维护方**：拆一步。上限保证它一定会停。假如它跑满 30 轮、每一轮都在做无用功——上限替你省了什么？

**用户：**

> 省了token

**维护方**（给答案，记 ❌；压缩）：它一轮都没少跑，省的只是第 31 轮以后的。上限是封顶不是止损——封顶保证会停，止损要求停之前干的事有意义；真实浪费是在上限之内做完全部无用功。止损靠验证器中途判偏再停掉。接着：用户按了一下 Esc，想让 5 个正在跑的子 agent 都停。这个「停」怎么传到它们那里？等它们自己发现？

**用户：**

> 靠调用工具，强制停止sub-agent？

**维护方**（给答案，记 ❌；压缩）：「比较可靠」不是停，停要的是保证；正在跑十分钟命令的子 agent这十分钟里一个字都读不到，你等的正是你要停的东西。取消必须是从外向内的独立通道：编排器直接把进程停掉，不经过任何模型；「工具」若是编排器自己动手就是它，若是主 agent 决定去调就又绕回模型。取消要留痕，否则主 agent 下一轮以为它们还在跑。最后一问：主 agent 派出子 agent 之后，是站在原地等它回来，还是继续干自己的事？哪个对？

**维护方**：拦——你选了一边。主 agent 派出去之后，它手上一定有别的事可干吗？一个研究型主 agent 把全部调研派出去了，自己这时候干什么？

**用户：**

> 可能是在等

**维护方**：对，那种情况它就是在等。「等」和「继续干」哪个对，取决于什么？一句话。

**用户：**

**维护方**：对，就是这句判据；按判据答，不按主流答。Q09 完。

## Q10

**第一问 · 维护方**：一个任务跑了 40 轮，第 3 轮用户说过「别动数据库」，第 38 轮它动了。为什么？

**用户：**

> 漂移了，第三轮的几个字，压不过后面35轮的几万token

**维护方**：对，主病因：还在但被压过去了。追一句：第 38 轮的时候，第 3 轮那句话一定还在上下文里吗？有没有另一种病因？

**用户：**

> 压缩了，压没了

**维护方**：两种病因齐了，治法完全不同。第二问：治「不在了」用什么，治「被压过去了」用什么？

**用户：**

> 不在了，用外部记忆保存，比如写在claude.md里面。压过去，靠每一次新的组装提示词的时候，把这条消息重新组装到最近的位置，作为提醒。

**维护方**：「不在了」→ 外置，对（CLAUDE.md 不参与压缩、进程死了还在、可改）。「压过去了」要拦：把那句话每轮放到最近位置——真实有人做、也有效，可这条提醒经不经过模型？放得再近也是几个 token 在竞价。什么东西能保证「别动数据库」，不管模型有没有读到它？

**用户：**

> 对，经过，还靠外部的代码，就是Hook或者是gate在拦

**维护方**：对。三层齐了：提示与外置是软的只提高概率；外置治「不在了」；hook 治「在但没照做」。天花板：所有记忆系统假设「注进上下文就会遵守」，这个假设是错的。后半题：把说明书写严、用 Q05 那套强制格式——schema 能防住工具调用的幻觉吗？

**用户：**

> 能防住格式上的幻觉，比如把key写错了，但是防止不了value里面的幻觉

**维护方**：对，schema 管形状（key）不管内容（value）。追一句：那我把 schema 写得越严越好——必填字段全部加上——会怎样？

**用户：**

> 把模型限制死了吧？模型无法自由发挥了，会变笨？

**维护方**（拆一步）：Q05 那条「推理会掉一截」是真的，但这里问的是幻觉。一个必填字段，模型不知道该填什么——它能空着吗？采样器允许它跳过吗？那它会填什么？

**用户：**

> 哦哦，会填一个近似的不真实的内容

**维护方**：对——必填 + 不知道 = 采样器不让跳过，只能编一个格式合法的值；schema 越严逼出的幻觉越多。第三问，你自己的案例：文档里 pH 该在 0–14，模型抽出了 12，校验器拦下了。然后呢——重试怎么重？

**用户：**

> 单开上下文，不要让之前的信息干扰。另外允许留空

**维护方**：两条都对；允许留空正好接上一问——必填逼幻觉，留空是解药。追一句：为什么不能在原上下文里告诉它「你上次答的超出范围了，再试一次」？省事得多——坏在哪？

**用户：**

> 那模型为了完成，会编造

**维护方**：对——它被训练成「给出一个能被接受的回答」，你告诉它超范围等于把答案范围泄露给它：换一个范围内的值而不是重读文档，把抽取错误变成了编造。追一句：干净重跑三次，三次结果是 12、6.8、7.5——这告诉你什么？和三次都是 12 比。

**用户：**

> 波动比较大，需要review

**维护方**：对——不一致 = 在猜，转人工；三次都 12 = 稳定读出同一个东西（值怪先看文档）。这个「确不确定」是从外面测出来的，不是模型自报的。最后一问：校验器（0–14）拦住了 12。文档写 7.2，模型抽成 6.8——校验器拦得住吗？那它到底在保证什么？

**用户：**

> 拦不住，保证的是合理，不保证准确

**维护方**：对——保证「不离谱」，不保证「对」；合理但错靠抽样人工、交叉验证，三次采样的不一致也能抓一部分。Q10 完。

## 跨题

**第一问 · 维护方**：这个模块反复出现一句判据。用它把今天说过的四样东西串成一句话：Q08 的清单、Q09 的超时和取消、Q10 的 hook、Q11 的沙箱。它们为什么是同一件事？

**用户：**

**维护方**：换个问法。模型要「知道」任何一件事——子 agent 干完了、进程挂了、第五步做完了——它唯一的途径是什么？

**用户：**

> 返回到context中，模型只能看到context中的内容

**维护方**：对——三句都是这一件事：模型只能读到被写进上下文的字，谁写的字决定它可不可信（编排器写的是事实，子 agent 写的是汇报，模型自己写的是自述）；没写进去的事对它不存在。复习结束，记分表另见记录。
