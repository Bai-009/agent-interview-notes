## 出题人：查证后的自我更正（四处）

> Thought for 11s
> 你的三个质疑，前两个我认，第三个正好是关键。我去查证据，不猜。
> Ran 5 commands · 1 note
> 找到了，你三条质疑，两条完全成立，我那个例子编错了。
>
> 一、深度上限：默认是 1，也就是根本没有孙子
> Codex 里有一个配置叫 `agent_max_depth`，默认值是 1。
> 意思是：主 agent 可以派子 agent，子 agent 不能再派。
> 而且拒绝的方式很直白——子 agent 想再派的时候，它拿到的回复是一句话：
> "已达到 agent 深度限制。自己解决这个任务。"
> 所以默认配置下，"孙子 agent"根本不存在。 我上一轮拿它举例，是编的。你的直觉对。
> （另外看到并发也有上限，配置项叫"每个会话最大并发线程数"，示例配置里写的是 7，而且界面上还有提示说别把它设到 8 以下会怎样——总之是个位数，和 Anthropic 那个 3-5 对得上。）
>
> 二、身份是预定义的——你也说对了
> Codex 里有一个内建 agent 的目录，里面躺着 `awaiter.toml`、`explorer.toml` 这类文件——每个是一个预先写好的角色，带着自己的职责说明、模型档位、超时设置。
> 不是主 agent 现场发明一个 agent 出来。它是从一份已有的名单里挑。
> 但有个区分要说清楚：身份是预定义的，任务是动态的。
> 主 agent 挑一个"探索者"，然后现场告诉它"去查 auth 模块"。角色固定，指令自由。
>
> 三、那还剩什么风险——这条你的质疑不成立
> 你说"肯定要设最大调用次数吧"——对，一定有。但上限的作用是封顶，不是止损。
> 想清楚这个区别：
> 上限保证它会停。它不保证它停之前干的事有意义。
> 具体场景：一个子 agent 上限 25 轮。它在第 6 轮就已经跑偏了——查错了方向，或者在两个方案之间来回横跳。它会老老实实转到第 25 轮才停。
> 那 19 轮，每一轮都在调模型，每一轮都在花钱，而且每轮上下文更长、更贵。
> 所以真实的浪费不是"无限循环"（那不存在），是"在上限之内做完了全部无用功"。
> 而且没有任何东西会发现这件事——它不会报错，它只是没干成活。 从外面看，一个跑满 25 轮返回"未找到"的 agent，和一个跑 5 轮返回"未找到"的 agent，长得一样。
>
> 四、所以停止机制到底防什么——我重说一遍
> 不是防无限循环。 深度限制和轮数上限已经把无限这件事封死了。
> 是防"已经没有意义了，但还在按上限跑完"。
> 举三个真实场景：
>
> * 用户按了 Esc。 你已经不想要这个答案了，但 5 个子 agent 还在各自跑到自己的上限。每一轮都在花你的钱，而结果没人要。
> * 主 agent 改主意了。 1 号返回的结果让它意识到 3 号那个方向没意义。3 号还在跑。
> * 预算到顶了。 整个会话的钱花完了，得让所有还在跑的立刻收手。
>
> 这三种情况的共同点：agent 本身没有任何问题，是外部世界变了。 它自己永远不会知道。
> 所以停止机制的作用，是让"外面的世界改主意了"这件事，能传达到一个正在闷头干活的东西那里。
>
> 五、我那句"烧钱"的正确版本
> 现在可以说准了：
> 孙子 agent 那个例子是我编的，默认深度是 1，不存在。
> **真实的浪费是这样的：**你按了 Esc，或者主 agent 改了主意，而那几个子 agent 还在各自转。它们不会无限转——但它们会转到各自的上限才停。
> 5 个子 agent，各剩 15 轮没跑完，就是 75 次没人要结果的模型调用。
> 这才是那个数字。不是无限，是一笔有上限但完全白付的账。
