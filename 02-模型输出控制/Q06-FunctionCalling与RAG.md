## ⚡ 30 秒速览（复习时只看这一块）

- **一句话回答**：FC 和 RAG **不在一个层面**——FC 是**机制**（模型输出长什么样），RAG 是**架构模式**（上下文里的信息从哪来）。它们不互斥，还能互相实现。真正的选择题只有一个：**检索的决定权，交给代码还是交给模型。**
- **必须覆盖的关键词**：`类别错误` `FC 是模型的输出，不管工具背后是什么` `模型动作` `RAG 是架构模式` `决定权在代码 vs 在模型` `agentic RAG = 用 FC 实现的 RAG` `Claude Code 拆掉向量检索换 grep` `控制回路 vs 单次直通`
- **上次的唯一短板**：**有了判断，却说成了自我怀疑。** 「我可能理解错了」应该是「**这题把两个层面的东西并列了**」。同样的内容，前者像不确定，后者像判断力。
- **答题骨架**：① 先拆题——这俩不在一个层面 → ② 给常规分法**并指出它不成立**（Claude Code 反例）→ ③ 真正的轴：决定权 → ④ 三条判据 → ⑤ 现实是混合

## 1. 题目原文

> Function Calling 与 RAG 的区别和联系，什么时候用哪个。

**出题人预先指出的误区**：题库标准答案（实时/结构化 → FC，离线/非结构化 → RAG）是**2023 年的分法**，2026 年已经不太站得住。
**预留的追问点**：FC 里如果那个"函数"就是"去搜文档"呢？那它到底算 FC 还是算 RAG？

**考察意图**：不是考两个名词的定义，是考**你能不能发现这个问题问错了**。照着题库那张表答，追问一句就会暴露。

## 2. 我的原始回答（不修饰，保留原样）

> 去搜索文档，搜索引擎本身就是工具，然后把搜寻到的片段，作为工具的结果返回。而RAG是向量化检索，是把query向量化后，做向量计算，找近似的内容。
>
> 这一点是我的理解，而且我觉得不对，因为工具调用其实也可以调用向量化模型，工具调用本身就是一个很宽泛的定义，与其叫做工具调用，不如我认为是模型动作，我派出多个子agent也可以被叫做工具调用。
>
> 但是我可能理解错了，你说的fiction calling如果指的是模型输出工具说明的契约的格式来调用工具，指的是模型的输出的话，那我上面说的就有问题。

## 4. 完整答案（面试可直接复述）

### 4.1 先拆题：这两个东西不在一个层面

| | 是什么 | 管什么 |
| --- | --- | --- |
| **Function Calling** | 一种**机制** | **模型输出长什么样**——这一轮不吐散文，而是吐一个结构化的请求：调哪个工具、参数是什么 |
| **RAG** | 一种**架构模式** | **上下文里的信息从哪来**——先检索、后生成 |

**FC 的全部内容就这么多。** 至于那个工具背后是搜索引擎、向量库、数据库、还是派一个子代理去干活——**FC 一概不管**。

> 所以「与其叫工具调用，不如叫**模型动作**」这个命名是准的：它描述的是**模型做了什么**，不是**被调用的是什么**。

**它们不互斥，而且可以互相实现：**
- **经典 RAG 完全不需要 FC**：代码在模型看到问题之前就检索完、塞进 prompt 了，**模型全程没有选择权**
- **agentic RAG 正是用 FC 实现的**：模型自己决定要不要搜、搜什么

### 4.2 FC 与 Structured Output 的关系（接上一题）

> **FC 就是 [[Q05-StructuredOutput]] 用在"我要做什么"这件事上**，再加两样东西：
> - 一条 **dispatch 约定**：外面的代码看到这个结构就去执行
> - 一段**后训练**：教它什么时候该吐这个、而不是吐散文

配上 Q05 推过的另一半：

| 方向 | 是什么 |
| --- | --- |
| **结构化输出** | 出口（概率世界 → 确定性世界） |
| **结果信封** | 入口（确定性世界 → 概率世界） |

**一去一回，就是模型和确定性世界的完整接口。**

### 4.3 为什么题库那张表不成立：一个反例就够

**Claude Code 检索代码。**

按题库分法：代码库是**离线的、非结构化的、私有的文档** → 标准的 RAG 领地。

**但它用的是 `Grep`、`Glob`、`Read` 三个工具，全走 FC。而且是把已经建好的向量检索拆掉之后才换成这个的。**

> **最该用 RAG 的场景，行业头部产品用 FC 干了，而且效果更好。**
> 你要是按题库那张表答，面试官追问一句「那 Claude Code 怎么回事」，就会暴露。

✅ **已查证，可放心引用**（细节见 7.5）：Claude Code 作者 **Boris Cherny** 公开说明——早期版本确实用过 RAG + 本地向量库，也试过基于模型的递归索引，最后**朴素的 glob + grep 赢了**，而且**"outperformed everything by a lot"**。

**他们给的四条理由，是工程理由不是精度理由**，报出来比只说"效果更好"有力得多：

| 理由 | 含义 |
| --- | --- |
| **security（安全）** | 不必把代码库喂进第三方索引服务 |
| **privacy（隐私）** | 同上，代码不出本地 |
| **staleness（陈旧）** | 索引永远落后于代码；grep 读的是**当前磁盘上的真实内容** |
| **reliability（可靠性）** | 少一套要维护、会失败、会不一致的基础设施 |

> 💡 **这四条里有三条跟"检索准不准"完全无关。** 这是本题最容易被忽略的一层：**放弃向量检索的主要动力是运维和信任，不是召回率。**

### 4.4 真正的分界线：决定权

| | 谁决定要不要检索 | 什么时候检索 | 检索错了会怎样 |
| --- | --- | --- | --- |
| **经典 RAG** | **代码** | 生成前，**一次** | ❌ 模型**不知道**自己拿到的是错料，照样自信作答 |
| **FC / agentic 检索** | **模型** | **循环内，按需多轮** | ✅ 模型能看到结果不对，**改词重搜** |

**这就是同一根轴：决定权放在代码里，还是放在模型里。**

> 学界的说法是同一件事：经典 RAG 是**固定的单次直通管道**（LLM 只在最后出场，从递给它的 chunk 里生成答案）；agentic RAG 把检索变成一个**控制回路**——**检索 → 推理 → 决定 → 再检索或停止**，LLM 全程在场，充当**推理引擎**。

**成本形状也跟着变**：经典 RAG 是**一次固定开销**；agentic 是**按需多轮**——难查询上更贵但更准，简单查询上是纯粹的开销浪费。

### 4.5 生产上怎么选：三条判据

判据**不是**"数据是什么类型"，是：

| # | 问什么 | 选哪个 |
| --- | --- | --- |
| **一** | 这个检索**用不用得着迭代**？ | 一次 top-k 就够（FAQ、明确的事实查询）→ **预检索**，省钱省延迟<br>需要"先找到线索、再顺藤摸瓜"→ **交给模型多轮** |
| **二** | **query 和语料的词对不对得上**？ | 精确标识符、函数名、错误码 → **字面检索 + 循环**<br>跨语言、同义改写、概念性 → **向量** |
| **三** | **语料活不活**？ | 每天在变 → **别建索引，现查**<br>基本静态 → 索引摊得起 |

> ⚖️ **但别把答案说偏了（查证补充）**：上面三条容易读出"agentic 更先进"的味道。**前沿的实际共识是——经典 RAG 因为「可预测」仍然是很强的默认选项**，agentic 是在任务**频繁需要重试、拆解、跨源交叉验证**时才更优。
> 学界给的另一组坐标是**查询复杂度 × 错误容忍度**：两者都低 → 经典 RAG 就够，多花的钱买不到东西。
>
> **面试里主动说出"经典 RAG 仍是强默认"，比一味吹 agentic 更贴近生产实践。**

### 4.6 现实：混合才是常态

最常见的形态是——**底下是向量库，但把它包成一个工具交给模型调**：

> **检索用向量，决定权在模型。**

这时候再问"这算 FC 还是 RAG"，**已经是个没意义的问题了**——而这恰恰证明了 4.1 那个判断。

## 5. 第一性原理

- **为什么这题是类别错误**：FC 回答的是「**模型这一轮的输出是什么形状**」，RAG 回答的是「**上下文里的东西是怎么进来的**」。一个在**输出侧**，一个在**输入侧**；一个是**格式**，一个是**流程**。拿它们二选一，等于问"是用 JSON 还是用缓存"。
- **为什么"决定权"才是真轴**：因为它决定了**错误能不能被发现**。代码决定检索 → 检索错了，模型拿到错料还以为是对的（这正是 [[Q04-幻觉成因与治理]] 说的"RAG 只治第 1 层，不治乱说"）。模型决定检索 → 结果进了上下文，模型**能看见它不对**，于是有了重试的可能。
- **不这么想会怎样**：按数据类型选型 → 遇到 Claude Code 这种反例就解释不了，因为**真正驱动那个决策的是陈旧性和信任，不是数据类型**。

## 7.6 基线核查（2026-08-28 · 第二轮）：这题在 2026 年的上位概念

**落后点**：本题把轴定在「决定权在代码还是在模型」——这个判断没问题，但 2026 年**行业已经把 FC / RAG 一起装进了一个更大的框**里，答题时不提这个框，会显得只在两个具体技术之间原地循环。

**那个框叫「上下文工程」（context engineering）**，2026 年的通行拆法是四根柱子：

| 柱子 | 内容 | 对应本仓哪一题 |
| --- | --- | --- |
| **指令** | system prompt、行为约束 | Q01、Q02 |
| **检索** | RAG 与实时搜索 | 本题、[[Q07-Embedding与检索策略]] |
| **记忆** | 短期会话 + 长期持久状态 | [[Q15-窗口内放什么与记忆压缩]] |
| **工具** | function calling 的可调用面，正在由 MCP 标准化 | 本题、[[Q11-MCP与Skill]] |

**这个框对本题的直接作用**：它把「FC vs RAG 是类别错误」这个判断从**否定**升级成**肯定**——不只是"这俩不该二选一"，而是"**它们是同一件事（决定模型看见什么）的两根不同柱子**"。

一句流传较广的分工说法可以借用：**RAG 负责"知道"，MCP 负责"做"**；再补上本题原有的轴——**谁来决定什么时候知道、什么时候做**。

> 💡 **另一处可以接上的新料**：[[Q05-StructuredOutput|Q05]] 的基线核查查到，XGrammar-2（arXiv:2601.04426，2026-01，v4 修订于 2026-08）专门为 agent 场景优化了**工具调用的语法编译速度**（>6×）与请求内动态切换。
> 含义是：**工具调用的工程瓶颈已经从"能不能约束住格式"移到了"几十上百个工具的语法能不能编译得够快、切得够灵活"。** 面试里提这一句，说明你知道 FC 在 2026 年的真实成本在哪。

- 延伸：[[Q11-MCP与Skill]]、[[Q19-生成模型评估]]、[[Q12-微调vsRAG]]

## 9. 核心结论

> **FC 和 RAG 不是二选一，它们不在一个层面：FC 是模型输出的形式，RAG 是上下文的来源。真正的选择题只有一个——检索的决定权，交给代码还是交给模型。**

查证后可以补充一条（这一条可以应对"是不是 RAG 过时了"的追问）：

> **Anthropic 把 Claude Code 的向量检索拆了换成 grep，四条理由里三条跟召回率无关——安全、隐私、索引陈旧。放弃索引的主要动力是运维和信任，不是精度。**
