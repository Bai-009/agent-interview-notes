## 1. 题目原文

> 多 Agent 架构下，主 Agent 和子 Agent 的通信链路应该如何设计？如何处理异常？

**出题人给的场景与三问**（原话）：

> 先给你一个具体场景再答，不然容易空对空：
> 主 agent 要改一个功能，派子 agent 去"把整个 repo 里所有调用了 `old_api` 的地方找出来"。

>
> 1. 子 agent 干活的时候，它的上下文和主 agent 的上下文，是同一份吗？
> 2. 它翻了三十个文件，最后回报一句"共 12 处，在这些文件里"。那三十个文件的内容去哪了？

> 第三问是这题的重点，慢慢想。

**考察意图**：题面听起来像在问架构图（消息队列？RPC？重试策略？），但三问把它压到了真正的考点上——**多 Agent 的通信链路不是网络问题，是上下文问题**。三问分别对应：隔离的动机（为什么必须是两份）、压缩的代价（信息在哪一步不可逆地没了）、可观测性的边界（一个只会读文本的东西，怎么知道另一个东西出事了）。第三问是筛人的那一问：它把「异常处理」从「加重试」拉到「异常必须先变成一段文字才存在」。

## 4. 完整答案（面试可直接复述）

### 4.1 一句话定义

多 Agent 的通信链路，本质是**两个不共享内存的无状态模型之间，一条单向的、有损的文本通道**。所以设计要点只有三条：**上下文为什么必须是两份**（经济学）、**回报在哪一步不可逆地丢了信息**（压缩）、**主 Agent 凭什么知道对面出了事**（可观测性）。异常处理全部落在第三条上——因为**一个只会读文本的东西，只能知道被写成文本的事**。

### 4.2 第一问：上下文是不是同一份——不是，而且理由是物理的

- **不是同一份。** 子 Agent 有自己独立的上下文窗口（Anthropic 一手来源已核实，见 7.5）。
- **动机不是「解耦好排查」，是上下文经济学**：
  - 主 Agent 的链条是**只增不减**的。子 Agent 在探索时读的三十个文件、走的两条死路，如果发生在主链上，就会**永久占据主 Agent 的窗口**——而且不只是占位，还会持续参与注意力竞争（[[Q03-Token与上下文窗口与上下文腐化]]：半相关内容的干扰强于完全无关内容）。
  - **试错的代价是永久的**：模型每轮失忆、靠重拼历史工作（[[Q08-Agent自主运行]]），所以主链上的每一条垃圾，此后**每一轮都要重付一次 token**。
  - 所以子 Agent 真正买到的东西是：**一个可以抛弃的试错场所**。它跑完就销毁，三十个文件连同两条死路一起蒸发，主链上只多了一句话。
- **代价要一起说**：多 Agent 系统的 token 消耗约为普通对话的 **15 倍**（Anthropic 一手数据，7.5）。所以它是一笔**用钱换主链纯净度**的交易，不是免费的架构升级——问「值不值」的判据是：**这次探索的中间产物，是不是注定要被丢掉？** 是，就派子 Agent；不是（后续还要反复引用原文），派了反而要再取一次。

### 4.3 第二问：三十个文件的内容去哪了——一次不可逆的有损压缩

- **没了。** 子 Agent 的上下文随它一起销毁，主 Agent 拿到的只有那句「共 12 处，在这些文件里」。
- 这是**通道的固有性质，不是实现缺陷**：官方文档对子 Agent 回报的定性就是**返回摘要而非原始输出**，理由写得很直白——避免有用信息被嘈杂的中间产物淹没（已核实，7.5）。**换句话说，有损是它的目的，不是它的副作用。**
- **不可逆性的位置值得单独记**：这和 [[Q07-Embedding与检索策略]] 的分块是同一类问题——**链路上最上游的那一步不可逆，后面所有环节的天花板都由它决定**。子 Agent 回报的那句话，就是主 Agent 关于这三十个文件所能知道的**全部**；它写漏了，主 Agent 没有任何办法发现。
- **所以协议的两条硬要求**：
  1. **下发要自包含**——子 Agent 看不到主 Agent 的上下文，凡是它需要的背景（约束、口径、已经排除的方案），必须写进任务描述里。默认它什么都不知道。
  2. **回报要留指针**——不能只给结论，要给**能被抽查的坐标**：文件路径、行号、原文片段。这是 [[Q04-幻觉成因与治理]] 证据门禁在多 Agent 上的形态：**不要求子 Agent 可靠，只要求它的错误可被检测。**
- **工业界已经把「抽查」做成了工序**：Anthropic 的研究系统在研究循环结束后，交给一个专职的 **CitationAgent**，用原始文档和报告逐条定位引用位置，确保每条论断都能归因到来源（一手来源，7.5）。

### 4.4 第三问（重点）：主 Agent 怎么知道——它不「知道」，它只读到一段文字

这是本题的题眼，答案要从 [[Q08-Agent自主运行]] 直接推：

- **主 Agent 也是个模型，它每一轮只看输入里的文本。** 「子 Agent 崩了」这件事，在主 Agent 眼里**必须先变成一段文字才存在**。
- 写这段文字的是 **harness，不是子 Agent 本人**（崩了的东西写不了遗书）。所以多 Agent 异常处理的第一性问题不是「怎么恢复」，而是——**谁负责把事件翻译成文字，翻译得诚不诚实。**
- **三种失败形态，可观测性完全不同**：

| 失败形态 | 有没有事件 | 主 Agent 能知道吗 | 靠什么 |
| --- | --- | --- | --- |
| **崩了**（进程退出、异常抛出） | 有明确事件 | 能 | harness 捕获后写进 tool_result |
| **卡住了**（没有任何事情发生） | **没有事件** | 不能 —— 除非人为制造一个 | **超时**：它的作用不是保护，是**把「什么都没发生」变成一个事件** |
| **跑偏了**（不崩不卡，正常返回了没用的结果） | 有事件，但是「成功」 | **不能** | 超时救不了 —— 只能靠验证器（[[Q04-幻觉成因与治理]]） |

- **第三行是最难的一行**，出题人的原话说得最清楚：*「从外面看，一个跑满 25 轮返回『未找到』的 agent，和一个跑 5 轮返回『未找到』的 agent，长得一样。」* 它不会报错，它只是没干成活——**这正是 [[Q08-Agent自主运行]]「end_turn 不是通行证」在多 Agent 上的放大版**：子 Agent 声明自己完成了，同样不作数。
- **可观测性的上限是结构性的**：那段代给模型看的文字由 harness 作者手写。出题人被拦下的第二处正是这个——多个子 Agent 的结果怎么合并，「是工具作者手写死在代码里的，不通用」。**所以「那段文字的诚实度，就是整个系统可观测性的上限」不是修辞，是架构事实。**
  一个真实的反例已经在 Codex 的 issue 里（已核实，7.6）：子 Agent 正常跑完但没被显式关闭，配额槽位不释放，后续 spawn 失败——而主 Agent 读到的那句话是 `collab spawn failed: agent thread limit reached`。**真实原因是「配额漏了」，写给模型看的是「到上限了」。** 主 Agent 拿着一句准确但误导的话，只能做出错误的下一步。

### 4.5 停止与取消：上限是封顶，不是止损

- **先把「无限循环」这个假问题排掉**：深度限制、轮数上限、并发配额都存在，**agent 不会无限跑**。
- **但上限只保证它会停，不保证它停之前干的事有意义**（出题人原话）。真实的浪费是：*「在上限之内做完了全部无用功。」* 一个子 Agent 在第 6 轮就跑偏了，它仍会老实转到上限才停，而每一轮上下文更长、单价更高。
- **所以停止机制真正防的，是「已经没有意义了，但还在按上限跑完」。** 触发它的三种情形（出题人给的，共同点极重要）：

| 情形 | 发生了什么 |
| --- | --- |
| 用户按了 Esc | 答案已经没人要了，但几个子 Agent 还在各自跑到上限 |
| 主 Agent 改主意了 | 1 号的结果说明 3 号那个方向没意义，3 号还在跑 |
| 预算到顶了 | 会话的钱花完，所有在跑的都得立刻收手 |

> **共同点：agent 本身没有任何问题，是外部世界变了——而它自己永远不会知道。**

- **推论：取消必须是一条从外向内的独立通道**，不能指望 agent 自己发现。这直接落在 [[Q06-FunctionCalling与RAG]] 的主轴上——**凡是必须被遵守的东西，都要放在代码层，不能只写成上下文文本**。Esc 是权限/进程层的能力，提示词约束不了它。
- **产品形态已经有了**：Codex 侧有 `close_agent` 关闭线程，以及一个默认开启的配置——中断某个 agent 的当前轮次时，**在记录里留一条中断消息**（`agents.interrupt_message`，默认 true，已核实）。这就是「取消也要留痕」的实现：**取消本身也得变成一段文字**，否则主 Agent 下一轮会以为那个子 Agent 还在跑。
- **边界**：取消的价值是**止损**，不是**回收**——已经花掉的 token 不会退。出题人把这笔账算过：5 个子 Agent 各剩 15 轮没跑完，就是 **75 次没人要结果的模型调用**。

### 4.6 同步还是异步——两种都真实存在

- **同步**：主 Agent 派出一批，等这一批全部完成再往下走。**这是目前生产系统的主流形态**——Anthropic 一手原文：他们的主 Agent 就是同步执行子 Agent，等每一批做完才继续；并把异步列为「会有帮助但尚未做」的改进方向，理由是协调与状态管理的复杂度上升（7.5）。
- **异步**：子 Agent 各跑各的，谁先完工谁先回报。原语在 Codex 侧是齐的（派发 / 等待 / 追加指令 / 关闭；等待支持长轮询，另有专门面向「等待与轮询」的内建角色）。
- **异步真正难的不是实现，是它引出的三件事**（出题人的收束，全部接得上前面的题）：

| 难点 | 为什么难 | 接哪一题 |
| --- | --- | --- |
| 半张图上的思考会**永久留在链上** | 主 Agent 基于「只回来了 3 个中的 1 个」做的推理，写进上下文就撤不回来了；后面两个到了也盖不掉前面那段错误铺垫 | [[Q03-Token与上下文窗口与上下文腐化]] 注意力零和竞价 |
| 每次唤醒都是**全额调用** | 模型无状态，「唤醒主 Agent」的物理动作是**把整段历史重新递一遍**——不存在「轻量恢复」这回事 | [[Q08-Agent自主运行]] 每轮重拼 |
| 失败发生在**你已经往前走了两步之后** | 同步下失败当场暴露；异步下主 Agent 已基于不完整信息推进了两步，错误只往下游传 | [[Q07-Embedding与检索策略]] 链路错误只往下游传 |

> 出题人对这三条的判断：**至今没有解决。** 面试里能把「异步不难实现，难的是这三件事」说清楚，比背出任何一种编排框架都有分量。

### 4.7 代价与边界（什么时候不该拆子 Agent）

- **中间产物还要复用时不要拆**——回报有损且不可逆，拆完再取一次更贵。
- **任务本身需要主链的隐含上下文时不要拆**——下发必须自包含，而「自包含」在复杂任务上经常写不全；写不全的部分子 Agent 不会问，它会猜。
- **15 倍 token 是入场费**，不是优化项。只有当「主链纯净度」的收益大于这笔开销时才成立。
- **不要把多 Agent 当并行加速用**：加速是副产品；主产品是上下文隔离。为了快而拆，通常会因为下发不自包含而返工。

## 5. 第一性原理

**根源只有一条：主 Agent 与子 Agent 之间没有共享内存，只有一条单向的、有损的、由第三方代笔的文本通道。** 四条推论全部由它导出：

1. **没有共享内存 → 上下文必然是两份。** 隔离不是设计选择，是默认状态；「让它们共享」才是需要额外成本的那个选项。这是 [[Q08-Agent自主运行]]「模型无状态」在多进程上的放大。
2. **通道是文本且有损 → 下发必须自包含、回报必须留指针。** 有损是目的（防止中间产物淹没结论），所以不能指望「把损失补回来」，只能指望「留下能抽查的坐标」。
3. **通道是事件驱动的 → 没有事件的失败在系统里不存在。** 崩了有事件、卡住没有——**超时的本质不是保护机制，是造事件的机制**。而「跑偏」连超时都造不出事件，只能靠验证器。
4. **通道是 harness 代笔的 → 可观测性的上限是那段代码的诚实度。** 主 Agent 的判断质量，不可能高于写给它看的那句话的质量。

一句收束：**多 Agent 的异常处理，最后全部归到「把一个事件翻译成一段文字」这一步——写不出文字的事故，对主 Agent 就等于没发生。**

不这么做会怎样：只加重试、只加超时，而不管「谁来写那句话、写得对不对」的系统，会稳定地产出一类最难查的故障——**每个子 Agent 都返回了「成功」，整件事却没做成，日志里一条错误都没有。**

- **异常处理在一手来源里的正面答案是「续跑」不是「重试」。** Anthropic 原文：出错时不能从头重启（代价高、且让用户难受），所以他们构建的是**能从出错位置接着跑**的系统。这是 4.4 三种失败形态之外的第四个问题——检测到之后怎么办。

### 📌 用词校准 / 最该记住的修正

1. **「我说同步，你说不对……我错」——这句认过头了。** Anthropic 一手原文写的正是**同步**：主 Agent 同步执行子 Agent，等每一批完成才继续；异步被列为「会有帮助但尚未实现」的方向。

2. **配置键名**：出题人写的 `agent_max_depth`，官方文档写作 **`[agents]` 段下的 `max_depth`**（`agent_max_depth` 这个写法出现在源码测试里，是同一设置的另一种拼法）。面试里说「Codex 有个 `agents.max_depth`」才对得上文档。

4. **「一个子 Agent 上限 25 轮」是出题人用来算账的举例数字**，不是某个产品的实测默认值。那笔「75 次白付的调用」的**推理成立**，但 25 和 15 两个数字不要当事实引用。

## 7.6 基线核查（2026-08-29 · 随首答一并核查）

> ⚠️ 本节内容不在讲解里，是维护方补的——每条先给锚点（接在哪句已会的话上），再讲新东西。

1. **「默认深度是 1，孙子 Agent 根本不存在」——这条已经过时，而且是被官方主动改掉的。**
   〔锚点：出题人第三处自我修正〕**原文说了什么**：默认深度 1，子 Agent 不能再派，所以递归不存在。
   **现在是什么**：这是**多 Agent v1** 的行为。2026-04-29 合并的一个改动把深度拒绝**从 v2 的派发处理逻辑里整个移除了**，理由写得很明确——`max_depth` 是 v1 的遗留护栏，v2 改用**任务路径路由**加**它自己的会话/线程配额**来约束，不应该再因为深度到顶就拒绝嵌套派发。该改动新增的测试用例名字直接叫「v2 派发忽略配置的 max_depth」。另有一份针对 0.144.1 的缺陷报告：设了 `max_depth = 1`，子 Agent 仍然成功生出了孙子 Agent，且**没有任何拒绝消息**——与上面的变更方向一致。
   **对答题的影响**：**护栏换了位置，但出题人那句判断反而更成立了**——「上限是封顶不是止损」原本是针对轮数说的，现在连「深度」这道封顶都不在默认路径上了，止损只能靠**配额**和**取消通道**。面试里若被问到，正确答法是：*「递归深度在早期版本有硬护栏，新版把它挪到了并发配额那一侧；所以不能假设『孙子不存在』，要假设『没人替你止损』。」*〔形态① 实现层翻代 + 结论翻转〕

2. **「异常」在生产里最常见的形态不是崩溃，是配额没回收——而且主 Agent 读到的那句话是误导的。**
   〔锚点：出题人第三句收束「那段文字的诚实度就是可观测性的上限」——这是它的实例〕
   一份仍未修复的缺陷报告：子 Agent **正常跑完了**，但因为配额的释放绑定在「显式关闭线程」而不是「跑完」上，槽位一直不释放；配额耗尽后，后续派发失败，主 Agent 读到的是一句 `collab spawn failed: agent thread limit reached`。同类现象还有：压缩上下文之后 Codex 持续报「Agent spawn failed」，尽管此前的子 Agent 早已结束。
   **为什么值得记**：这句错误提示**语法上完全正确**——确实是到了线程上限。但它把「资源泄漏」说成了「用量到顶」，主 Agent 据此只会做出「等一等再试」或「减少并发」的错误决策，而真正该做的是**关闭那些已经结束的线程**。**这就是「harness 代笔」的风险落地成本的样子。**〔形态③ 缺上位概念：异常处理不只是捕获错误，是**保证写给模型的那句话与真实原因对得上**〕

3. **内建角色的名单正在变动，`awaiter` 尤其不稳。**
   〔锚点：出题人举 `awaiter.toml` 为异步存在的证据〕出题人举的这个角色**确实存在过**，但仓库里已有一条「移除 awaiter」的提议，理由是它没有提供独有能力；当前官方文档列出的内建角色是 `default` / `worker` / `explorer`，另有来源列出面向长时间轮询的 `monitor`。
   **对答题的影响**：**结论不变、例证要换**。异步形态确实存在（等待/轮询原语是齐的），但**别把 `awaiter` 当成一个稳定事实报出去**——报一个正在被删的角色名，正是 [[Q02-SystemPrompt与Fewshot与CoT]]「报不动的引用不如不报」的现场。改报原语（派发 / 等待 / 关闭）更稳。〔形态① 实现层翻代〕

4. **题目集合漂移**：题库原始只有「主子 Agent 通信与异常」一行标签，而出题人给出的是**场景题 + 三问**，重点落在可观测性与取消语义上。这与[台账](../00-索引/基线核查台账.md)记录的漂移方向（**Multi-Agent Harness、Loop Engineering、可观测性**）完全吻合——**考法已经从「画通信链路图」漂到「上下文经济学 + 异常可见性」**。第二期 `Txx` 出题时，这一格应当出到「取消语义」「回报协议」这一层，而不是「怎么设计消息队列」。

- **前望**：[[Q14-推理降本与多Agent权衡]]（15 倍 token 的成本账）、[[Q15-窗口内放什么与记忆压缩]]（子 Agent 断点续跑的状态住哪）、[[Q17-执行链路与连续任务正确性]] / [[Q18-长任务不偏离目标]]（四层停止的完整落点）、[[Q20-工具调用安全]]（下发自包含与权限边界）

---

## 9. 核心结论

> **子 Agent 买的不是并行，是「试错发生在别人的链上」——代价是回报必然经过一次不可逆的有损压缩，所以下发要自包含、回报要留指针。而主 Agent 从不「察觉」任何事，它只读到 harness 代笔的那段文字：崩了有事件、卡住没有事件（超时的作用是造事件）、跑偏连超时都造不出事件（只能靠验证器）。所以多 Agent 的异常处理，最后全部归到「把一个事件翻译成一段文字」这一步——写不出文字的事故，对主 Agent 就等于没发生；而那段文字的诚实度，就是整个系统可观测性的上限。**
